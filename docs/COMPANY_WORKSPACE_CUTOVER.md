# Company ClickUp MCP cutover — isolated, owner-controlled

**3 November 2026 SAST.** The operator approved preparing company Workspace connectivity and explicitly requested **read/write capability without destructive actions**. The separate first-party *work* ClickUp account verified read access to the shared work List. This does not prove company MCP deployment, authorization for arbitrary Writes, or permission to alter live records without a specific instruction.

## Deployment boundaries

The existing staging/serviteur Worker, personal dummy Workspace, OAuth account, encrypted Durable Objects and KV remain unchanged. Provision a **second** company Cloudflare Worker named `clickup-serviteur-company`, with a dedicated OAuth KV namespace and independently scoped GitHub/ClickUp OAuth clients, company-only Cloudflare secrets and per-user encrypted Durable Objects.

The new company profile has **read plus opt-in write** capability: `CLICKUP_COMPANY_PROFILE=true` and `CLICKUP_COMPANY_WRITE_MODE=non_destructive` enforce a reviewed operation allowlist server-side. All deletions, removals, moves, doc-page replacement, unknown mutations, Workspace authorization expansion and List retargeting are forbidden; the company MCP hides these actions. A missing or unrecognized company write mode fails closed. The optional OAuth `mcp:write` grant still requires the user's separate consent. The verified resource scope remains `list` and does not grant Workspace-wide authority or arbitrary List IDs. The employee account need not belong exclusively to one Workspace for this List-only mode.

The work List appears under **Shared with me**. A verified List may therefore be absent from the ordinary `/team/{workspace}/space` endpoint; the fallback calls ClickUp's officially documented **Shared Hierarchy** endpoint `/team/{workspace}/shared`, accepting ONLY an exact List ID in that Workspace's `shared.lists`. A successful GET of the List alone does not grant access.

## GitHub and Cloudflare setup (owner actions)

1. Create a protected GitHub **company** Environment, restricting deployment to the reviewed main branch. Add **variables**: `COMPANY_WORKSPACE_ID`, `COMPANY_LIST_ID`, `COMPANY_GITHUB_OWNER_ID`, `COMPANY_CLICKUP_USER_ID`, `COMPANY_OAUTH_KV_ID`, `COMPANY_PUBLIC_ORIGIN`, and (if available) `STAGING_OAUTH_KV_ID` and `STAGING_PUBLIC_ORIGIN` for independent-KV/origin validation. The Workspace/List/user IDs must be those independently verified in the work ClickUp connection; do not use the dummy IDs.
The company Worker hostname should remain generic, for example `https://clickup-serviteur-company.<your-worker-subdomain>.workers.dev`. Use the actual assigned HTTPS origin for `COMPANY_PUBLIC_ORIGIN`; do not place the employer's name or company account IDs in GitHub source or public documentation.

2. Create a fresh Cloudflare OAuth KV namespace only for the company Worker. Create separate OAuth applications/credentials with callbacks bound to the **company-specific exact HTTPS origin**; never reuse dummy OAuth client secrets, token encryption keys or KV. In the GitHub company Environment, set **secrets** `COMPANY_CLOUDFLARE_API_TOKEN` (least-privilege) and `COMPANY_CLOUDFLARE_ACCOUNT_ID`. Do not put any keys in source, PRs or ChatGPT.
3. Configure the company Worker's **secrets** through Cloudflare: `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `CLICKUP_CLIENT_ID`, `CLICKUP_CLIENT_SECRET`, `CLICKUP_STATE_KEY`, `CLICKUP_TOKEN_KEY`. Use independent company OAuth applications and account-bound identity mapping. The manifest generator supplies only non-secret configuration variables and reserves separate Worker/KV/DO bindings.
4. After exact-head CI, CodeQL and Codex review, **manually** run GitHub Actions **Deploy ClickUp MCP company (manual, non-destructive read-write)** from reviewed main. It runs strict security/TypeScript/Vitest checks again before deploying. This is a company-only deployment; it does NOT overwrite staging.
5. Add the company MCP as a **separate ChatGPT Plugin** at its own HTTPS origin. First complete individual GitHub MCP OAuth; then call `connect_clickup_account` on the **company plugin**, open its one-time authorization URL and authorize the **work ClickUp user**, never the personal dummy user.
6. Start with read-only smoke: confirm the connected work user, exact configured Workspace and List, and bounded task reads. Confirm actual Shared Hierarchy fallback compatibility. With `list` scope, the company MCP permits creating tasks **and editing existing tasks**: title, description, status, assignees, priority, due date, custom fields, comments, attachments, tags, links, dependencies and supported time entries. Before each task-ID operation, it reads that exact task and verifies its home List in the authorized Workspace; the same rule applies to each task in a bulk update or relationship. Foreign-List and malformed records are rejected. Test writes only with an explicitly approved company QA task or the specific real task the operator has instructed it to modify.

**Read/write does not mean delete or unrestricted Workspace access.** Exact per-operation allowlisting is enforced before individual OAuth credentials are retrieved. Existing-task edits are allowed under the configured List grant after a live home-List preflight; no Workspace-exclusive OAuth requirement is added. ClickUp's task-ID update endpoint does not offer an atomic list-membership condition, so simultaneous external task moves between the preflight and the update remain a documented race, not a claim of transaction-level isolation. Deletion, tag/dependency removal, moving tasks to other Lists, replacing Doc content and Workspace-authority expansion remain excluded. Respect company permissions and explicit user instructions before any live write.

## Rollback and limitations

Disable or disconnect the **company** plugin or Worker to revoke its access; staging remains intact. The company operator must configure OAuth callbacks and Cloudflare credentials; GitHub code review/merge alone cannot complete that authorization. The company account may have limited access to shared Lists: never infer Workspace-wide permission from one valid List.
